# OOPLab2
# Лабораторная работа №2: Игровая база, ландшафт и нейтральные объекты

## Архитектура проекта

Проект разбит на логические модули:
*   `Unit.h` / `UnitFactory.h` — иерархия юнитов (Абстрактная фабрика).
*   `Base.h` — класс базы (реализует паттерн «Наблюдатель»).
*   `GameField.h` — игровое поле, контейнер для юнитов, терраина и объектов.
*   `Terrain.h` / `TerrainProxy.h` — ландшафт (паттерн «Прокси»).
*   `NeutralObject.h` / `Strategy.h` — нейтральные объекты и паттерн «Стратегия».
*   `Operators.h` — перегрузка операторов для взаимодействия.
*   `main.cpp` — демонстрационные сценарии и игровой цикл.

## Обоснование ключевых решений

### 1. Паттерн «Наблюдатель» (Observer)
**Где:** `Base::onUnitDeath()` и вызов из `Unit::takeDamage()`.
Реализовано 2 базы (своих и врагов), каждая ведёт свой реестр.
**Почему так:** База не должна постоянно опрашивать всех юнитов («Ты жив? А ты?»). Вместо этого юнит сам уведомляет своего владельца (`ownerBase`) о своей смерти. Это экономит ресурсы и соответствует паттерну.
**Решение проблемы удаления:** База получает уведомление и уменьшает счётчик. Однако, чтобы избежать циклической зависимости (`Base` -> `GameField` -> `Base`), удаление с поля происходит через метод `GameField::removeDeadUnits()`, который вызывается в `main.cpp` после действий.

### 2. Паттерн «Прокси» (Proxy)
**Где:** `TerrainProxy`.
**Почему так:** Прокси выступает как «заместитель» реального терраина. В моей реализации он добавляет проверку на оглушение (`isStunned`). Если юнит оглушён, Прокси блокирует проход, даже если сам терраин проходим. Это позволяет добавлять новые правила (например, «юнит под эффектом не может ходить») без изменения классов `Plains`, `Forest`, `Swamp`.

### 3. Паттерн «Стратегия» (Strategy)
**Где:** `InteractionStrategy` и классы `AttackBoostStrategy`, `HealthRestoreStrategy`, `ArmorBoostStrategy`. Используется в `Altar`.
**Почему так:** Алтарь должен по-разному влиять на разные типы юнитов. Вместо `if (type == "Infantry") unit.addAttack(5)`, мы выносим логику в отдельные классы-стратегии. В методе `interact` Алтарь динамически выбирает нужную стратегию на основе `unit.getType()` и вызывает `apply()`. Это делает код расширяемым (легко добавить новую стратегию для нового типа юнита).

### 4. Перегрузка операторов
**Где:** `Operators.h`.
**Почему так:** В задании требуется реализовать взаимодействие через перегрузку. Я сделал глобальные функции `operator+`, `operator-`, `operator*`, `operator/`. Внутри они вызывают стандартный метод `interact()` у объекта. Это позволяет писать красивый код: `*unit + *chest;` и одновременно сохраняет полиморфизм (все объекты наследуются от `NeutralObject`).

### 5. Управление памятью и удаление мёртвых юнитов
**Почему `removeDeadUnits` в `GameField`:** Юнит не должен знать, где он находится (это нарушает инкапсуляцию). Поле (контейнер) само должно чистить свои элементы. Метод `removeDeadUnits` проходит по сетке и удаляет юнитов с `health == 0`. Вызывается после каждого действия в `main.cpp`.

### 6. Хранение баз на поле
**Почему `Cell` хранит `Base*`:** База — это статичный объект, который занимает клетку. Поле должно знать, где находится база, чтобы:
1.  Отрисовывать её (символ `B`).
2.  Блокировать вход вражеским юнитам (`gameMoveUnit` проверяет цвет базы и юнита).

### 7. Движение и очки перемещения
**Почему `maxMovementPoints`:** Для того чтобы в начале каждого хода можно было восстанавливать очки движения (`resetMovement()`). В классе `Unit` хранится и текущее, и максимальное значение. Это позволяет легко реализовать замедление от терраина (стоимость шага может быть больше 1).

## Как играть (Демонстрационные сценарии)

В главном меню выберите пункт **7**, чтобы запустить демонстрацию. Сценарии показывают:
1.  Создание поля и баз (Синяя и Красная).
2.  Создание юнитов через базу (с проверкой лимита).
3.  Взаимодействие с ландшафтом (вывод эффектов клетки).
4.  Взаимодействие с объектами (перегрузка операторов).
5.  Уведомление базы о гибели юнита (Наблюдатель).
6.  Работу Алтаря (Стратегия).

Также доступен пункт **9** (Начать игру) — пошаговый режим с ходами, где можно увидеть всё в интерактивном виде.

В меню хода юнита есть выбор "Атака". Атака пока не реализована (это задача следующей лабы), сейчас там просто завершение хода. Этим я показываю, где будет располагаться отака в будущем.
